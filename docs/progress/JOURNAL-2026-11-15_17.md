## 2026-11-15 换官方 Data seed（本轮最大收益）

阶段 7 一直卡在「launchd 起来后成片崩溃」，当轮特征是
`Too many corpses` 93 次、`no system container/group/application group` 23 次、
`dyld_shared_cache_arm64` deny 68 次、SpringBoard 从 pid 26 一路重启到 227。

四个 `disable-jobs` 已按官方参数生效（崩溃名单里不再有 identityservicesd / locationd /
CommCenter / iconservicesagent），但没解决阻塞。于是按官方 skip-setup 教程换 seed：

```
tools/host/extend-fat-kernel.py out/boot-s7pmgr-official.img out/boot-s7pmgr-skip-ext.img \
    --need 540816 --path Payloads/scratch-data.img
tools/host/build-boot-swap-seed.py --base out/boot-s7pmgr-skip-ext.img \
    --seed work/ci-43688605493/data-skip-setup.dbr --out out/boot-s7pmgr-skip.img
```

产物 81,309,696 B，`out/boot-s7pmgr-skip.img`，SHA-256 `aff8b7c2958e0026d26aa04949f6d1d77d05d6e0002e062db1681d6242ec7f75`。
官方 seed 540,816 B，SHA-256 `8f88eac83c7e7d3bf1414b8b002e04fbdc5dcf26c9a34d7221e5b4b152398e`。

读回 `boot_id 0x267a1232`：`uptime_s 2354`、`rounds 254`、`phase 5 published`、
`write_errors 0`、254 个槽全 `stage=done stalled=0s`。崩溃类计数全部归零。**这是目前最好的一轮。**

同镜像 `--reset` 复跑得 `0x266eff40`（1115 s / 130 轮 / 0 写错），证明持久 Data 是 resume 而不是重建。

### 顺带纠正两个错误判据

- 窗口头 `state=2` 是 `NativeUfs.cpp` 里的常量，与 Data persist 无关；Data 侧 state 语义在
  `NativeRamBlock.cpp`（0 off / 1 blank / 2 resumed / 3 fresh / 4 refused / 5 degraded / 6 resumed RO），
  而且这个变量不打印。
- `slots.bin` 每个槽是**状态快照**，不是 msgbuf 副本。所以「254 个槽零崩溃 ⇒ 39 分钟全程零崩溃」
  这条推理不成立，只能证明可见窗口干净；要看全程得逐槽扫。

## 2026-11-15 SMP 重测

PMGR 修复前 SMP 会静默挂起，一直靠 `cpus=1` 规避。`sheng-smp=1` + 去掉 `cpus=1` 后：
`ml_processor_register` 16 行覆盖 cpu 0..7，两次启动分别到 44.5 s 与 54.1 s，都越过旧的
34.8–37.9 s 挂起点，`No PMGR` / panic 均为 0。**结论：`cpus=1` 不再是硬必需**，但两次都是切 EDL 太早，
没有长跑，所以 SMP 长稳仍未证明。

## 2026-11-15 → 16 GPU addon（参数不能代替实体）

官方 `native-adreno.md` 要求 `sheng-gpu-addon=1` 且把 `NativeAdrenoMetal.publish` 写进 **Data seed**。
先只加了参数（`boot-s7v5pon-gpuaddon.img`），读回 `0x1b6783fe`：GPU 计数全 0。
根因是 payload 里没有 `NGPUADD2` 容器，参数空转。

随后补齐构建链：CI 仓新增 `make-gpu-addon.py`、`check-offline-metal-addon.py`、`OfflineMetalAddon.h`、
`zzy-native-gpu-addon-mount.patch`、`make-owner-trust-bundle.py`；本机新增
`tools/host/inject-gpu-addon.py`（写 FAT sidecar `Payloads/kernel.macho.gpuaddon`、ADT `GpuAddon` 属性、
三合一 owner trust）。

CI 修了五轮才全绿，每轮都是环境问题而不是逻辑问题：

1. Python 3.15 没有 `distutils` ⇒ 固定 3.12 并装 `packaging/mako/pyyaml`。
2. `NativeAdrenoABI.h` 缺失 ⇒ `submodules: true` + Rust/LLVM/shaderc + pinned `metal2vulkan`。
3. `gen-turnip-replay.py` 需要 host Turnip ⇒ `--target host` + replay 输入 + vulkan headers。
4. `Translator patch result differs...` ⇒ runner 本地放宽纯文本 guard。
5. `inject-gpu-addon.py` 自测暴露 ADT 属性长度、LFN 没补 NUL、trust loader 校验过严 ⇒ 逐个修。

产物 `out/boot-s7v5-ngpu.img` 93,380,608 B，`sidecar / GpuAddon / dtb / trust` 四项全 True，
9 个文件进 sidecar。**但这颗镜像只跑到 34.2 s**，GPU 仍 0，说明 addon 存在不等于被加载。

## 2026-11-16 union 分支：先纠正事实，再证明那是退步

`nx729j_stage7_defconfig` 原本记着「union 会造成 copy-up 写风暴，所以关掉」。核对官方
`NativeUfs.cpp` 后确认 **`op 0x28` 是 READ(10)、`dir 2` 是 toHost**，那 13,000 多条 128 KiB 是读，
不是写。而且 union 关掉的 `0x1807cbc2` 里同样有这条读流 ⇒ 读流的成因是 dyld 在读共享缓存。

于是把 union 开回来（对齐官方 `nx729j_defconfig` 与 sheng 的组合），新增
`configs/nx729j_union7_defconfig`，并修了补丁自身的一个真 bug：`mountpoint_fallback` 与
`environment` 声明在 `#if !union` 分支里，使用处没有同条件 ⇒ **union=1 根本编不过**。
改成两分支都声明、只在 copyout 处区分用途，行数不变、hunk 头不动。

CI run `43785071512` 成功（620 s）。读回 `0x1f44cebb`：`cache mount target /`、
`probe cache dir err=0` 说明 union 生效，但 **`SRT: setup` 0 条**，39.4 s 结束。
结论：union 让挂载点正确，却丢掉了 v5pon 已经拿到的 shared cache 映射。**回退到 v5pon 基线。**

## 2026-11-16 34 秒复位归因：看门狗，不是 panic

同一颗 `boot-s7v5pon.img` 在 11-15 跑过 39 分钟，11-16 重刷只跑 34 秒。差异不在镜像，
而在**引导器这次把 Gunyah 看门狗 armed 了，内核从不喂狗**。只读探针原文：

```
NX729J_PON_PROBE psci v10001 reset=0 reset2_32=0 reset2_64=0 |
gunyah_wdt status=0 since_ping=22229ms |
spmi v70000001 apids=768 open=0 find=0 apid=565 owner=0 sdam48=00 read=0
```

`status=0` 即 armed，`since_ping` 22 s 时复位，与 34 s 处日志中断吻合。PMIC 复位原因仍取不到
（`open=0`，SPMI slave 从未打开，`sdam48=00` 是占位）。

据此写了喂狗补丁：仓库内 `patches/stage7-wdt-keepalive.patch` +
`scripts/prepare-stage7-wdt.py`（`--check` 幂等，基线通过、重复打补丁被拒）+
`scripts/check-stage7-wdt-keepalive.py`。**尚未编进内核，也尚未上机。**
